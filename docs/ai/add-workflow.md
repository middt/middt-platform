# Playbook: add or change a workflow

Definitions are JSON(C) files in `demo/Middt.Demo.Workflows/Workflows/` (`customer-onboarding.json`, `credit-allocation.json`, and `order-payment-orchestration.json` are full examples: `dataSchema`, `icon`, rules, subflows, `fanOut`, `loadWorkflow`, `cache`, roles, timers, and backend-driven `view.layout` screens; `invoice-collection.json` shows message-driven `Event` transitions, a `background` task and `history: delta`).

1. **Definition & Dynamic Menu / List Columns**:
   - Top-level properties: `key`, `version`, `title`, `description`, `icon` (Material icon rendered automatically in the sidebar menu of both frontends), `roles`, optional `instanceAccess` (`{ "mode": "owner", "supervisorRoles": [...] }`), `dataSchema`, optional `history` (`full` default, `delta`, `none`) and `historySnapshotEvery` (delta only, default 20), `timeout` (`{ "after": "PT48H", "target": "<state>" }` fires when the instance is still running), workflow-level `onError` (default policy for every task), `sharedTransitions` (transitions offered in several states; each lists its states in `availableIn`, `"*"` = every non-final state), `start`, `states` (`key`, `title`, `description`, `type` `Initial` | `Intermediate` | `Finish` | `SubFlow`, `subType` `Human` | `Success` | `Error` | `Cancelled` | `Timeout`, `step`, `view`, `onEntry`, `onExit`, `transitions`, `subFlow`, state-level `onError`), and `x-layout` (designer node coordinates written by `/workflow-admin`; harmless to omit).
   - **Deploying**: `POST /api/workflows/definitions` (and the demo's `DemoFlowDeployer`) **overwrites the stored definition with the same `key` + `version` in place** – there is no version comparison (that exists only for layouts). Running instances of that version immediately follow the new state machine, so bump `version` when the change must not touch in-flight instances (the old version stays stored and active instances keep their `DefinitionVersion`). In the demo, re-run `docker compose up -d --build middt-demo-workflows` after editing a file; hosts using `AddDefinitionsFromDirectory` load the files at startup.
   - **Transition properties**: `key`, `target` (state key or `$self` to stay in the state – a data update; with `"reenter": true` the state's `onExit`, `onEntry` and timers run again), `trigger` (`Manual` default, `Automatic`, `Scheduled`, `Event`), `title`, `description` (shown to users and handed to AI agents for routing), `style`, `icon`, `toolbar` (default true; `false` hides the button from the instance toolbar so it is only reachable from layout `rowTransitions`), `rule`, `default` (the automatic "else" branch), `roles` / `denyRoles`, `availableIn` (shared transitions), `input`, `onExecute` (tasks run before the target state), `view` (`{ "inline": true }` renders the input form as a wizard step inside the instance screen instead of a dialog; `component` names a registered Razor view).
   - **State `view`**: `{ "layout": "<layout-key>" }` (JSON layout, editable at runtime) or `{ "component": "<name>" }` (a Razor component registered with `[WorkflowView("name")]`). **`subFlow`**: `{ "workflow", "input", "into", "output" | "select", "forwardTransitions" }` – `forwardTransitions` (default true) forwards manual transitions executed on the parent to the active child.
   - **Tasks** (`onEntry`, `onExit`, `onExecute`): `{ "task", "key", "when" (expression; the task is skipped when false), "config", "onError", "background" }`. **`onError`** (task → state → workflow fallback): `maxAttempts` (1 = no retry), `delay`, `backoffMultiplier` (2.0), `maxDelay`, `useJitter` (±20 %), `retryOnStatusCodes` (`"502"`, `"5xx"`, `"!4xx"`; empty = retry all errors), `action` `Fault` (default: instance Faulted + incident) | `Transition` (run `transition`) | `Continue` (record an incident, go on).
   - `version`: used for the immutable runtime versioning below; see step 7 for `PUT .../definition`, which always creates a new version.
   - **History**: keep `full` unless the history grows large. `delta` stores mostly the change per transition (a JSON Patch) with a snapshot at the first and final row, every `historySnapshotEvery` rows and when a patch saves nothing. `none` writes no history rows – the instance data is still saved on every transition; use it for one-shot or high-volume flows whose audit lives elsewhere. What a row looks like, how the patch is produced and how to read versions back: [README – History modes](../../README.md#history-modes-and-how-json-patch-is-used).
   - If no external system sends the messages yet, give the same step a manual twin (as `record-payment` next to the `payment-received` event transition in `invoice-collection.json`) so it can be driven by hand.
   - **`dataSchema`**: Declares the JSON Schema for the workflow's `Data` document. Both frontends automatically generate the **workflow instance table columns** (`/workflow/{key}`) from `dataSchema.properties` in property order.
     - Set `"x-list": false` on any property you want to hide from the list table while keeping it in the schema.
     - Set `"x-search": true` (or a mode: `"text"`, `"select"`, `"range"`, `"min"`, `"max"`, `"gte"`, `"lte"`, `"date-range"`) to add a filter control to the workflow instance list toolbar; numeric properties become `_min` / `_max` bounds and the toolbar gains `createdFrom` / `createdTo` once any field is searchable (root `"x-date-search": true | false` forces or suppresses them).
     - Set `"x-index": true` to force a B-Tree index on the property (or `false` to suppress one); by default only `x-search` properties that are `enum`, `number`, `integer` or `boolean` are indexed.
     - Use `"x-mask": { "pattern": "last4" | "email" | "***", "exceptRoles": ["manager"] }` for sensitive field masking (the only accepted syntax – a string value is rejected by the validator; masked fields are never indexed) and `"x-roles": ["manager"]` for field-level role visibility.
     - Without a `dataSchema` the instance list falls back to `start.input.schema.properties`.
   - Expressions in `rule`, `input.rule`, and `set` tasks use the server-side C# dialect (DynamicExpresso): `data.Amount > 500000`, `user.IsInRole("Manager")`, plus JSON array helpers `data.partialPayment.Sum("amount")`, `data.partialPayment.Any("reference", input.reference)`, `data.partialPayment.Find("reference", input.reference)`, and `data.partialPayment.Remove("reference", input.reference)`.
   - **State availability `rule` vs. input validation `input.rule`**:
     - `transition.rule` evaluates whether the transition is available in the current state (`data`, `instance`, `user`, `now`).
     - `transition.input.rule` evaluates when the transition is executed or when an event message arrives (`input`, `data`, `instance`, `user`, `now`), rejecting invalid input with 409 before tasks run (e.g., `"rule": "input.amount <= data.remainingAmount"`).
   - **Declarative button appearance (`style` & `icon`)**: Set `"style": "primary" | "success" | "danger" | "warning" | "secondary"` and `"icon": "<material_icon>"` directly on a transition definition (e.g., `"style": "danger", "icon": "delete"` on `delete-payment`).
   - A new version's access rules apply only to its instances. When changing `roles`, `instanceAccess`, or supervisor roles, check both old and new instances in the list and detail endpoints.

2. **Validation** runs at startup and during HTTP deployment (`POST /api/workflows/definitions`) – fix every reported error; add validator rules in `WorkflowRegistry` for new definition properties (with tests in `tests/Middt.Framework.Tests/Workflow`).

3. **Screens per state (100% Backend-Driven JSON)**:
   - Every `Human` and `Finish` state should specify `"view": { "layout": "<layout-key>" }` pointing to a `kind: "view"` JSON layout in `demo/Middt.Demo.Workflows/Layouts/` (e.g., `kyc-review.json`, `credit-review.json`, `order-review.json`, `order-result.json`, `risk-detail.json`, `invoice-detail.json`, `ai-dispute-detail.json`).
   - Reuse common partial layouts across multiple workflow views with `{ "widget": "layout", "key": "workflow-footer" }` (see [`backend-driven-json-ui.md`](backend-driven-json-ui.md)).
   - **Transition forms**: Define `input.schema` on transitions (`JsonSchemaForm` in Blazor / `MiddtJsonSchemaFormComponent` in Angular).
     - **Appending and indexing arrays (`into: "<array>[]"`, `[-1]`, and `[N]`)**: Setting `"into": "partialPayment[]"` (top-level array) or `"into": "billingContact.emails[]"` (nested array) appends the validated input object to the target `JsonArray` (creating intermediate objects/arrays if needed). Target paths in `into` and `set` also support `[-1]` (last element, e.g., `"set": { "billingContact.emails[-1].addedAt": "now" }`) and fixed non-negative indexes `[0]`, `[1]`, … (e.g., `"into": "billingContact.emails[0]"` or `"set": { "billingContact.emails[0].email": "input.email" }`, with automatic form prefill in `WorkflowUi.StepPrefill` / `workflowStepPrefill`). In expressions and UI templates, elements can be read via index (`data.billingContact.emails[0].email`), iterated with the `list` widget (`"source": "data.billingContact.emails"`), or queried/modified with `.Any(...)`, `.Find(...)`, `.Sum(...)`, `.Last(...)`, `.Remove(...)`, `.RemoveAll(...)`, `.RemoveAt(...)`, and `.With(...)` (with removed items exposed in `input.removed`).
     - **Dynamic enum from instance array (`x-enumFrom`)**: Setting `"x-enumFrom": "partialPayment.reference"` or `{ "source": "partialPayment", "format": "{{ row.reference }} ({{ row.amount }} ₺)" }` on a schema property dynamically populates `enum` and `default` from the current instance's array when `GetAsync` projects `AvailableTransitions` (and formatted labels are registered via `JsonDynamic.RegisterFormattedLabel` so `.Remove("reference", input.reference)` / `.Find(...)` / `.Any(...)` match the selected item).
     - **Partial updates (`input.format: "jsonPatch"`)**: `"input": { "format": "jsonPatch", "into": "<owned subtree>", "schema": { … } }` makes the body an RFC 6902 JSON Patch on `data.<into>` (both `into` and `schema` are required; the schema validates the subtree after the patch; a failed `test` is 409). Works for flat/nested/indexed objects (`"into": "billingContact"` or `"into": "billingContact.emails[0]"`) as well as root or nested arrays (`"into": "partialPayment"` or `"into": "billingContact.emails"` with `schema.type: "array"` and paths like `"/0/email"`, `"/-"`, `"/1"`). For object schemas, both frontends prefill the form with the current values and send only the difference; for array schemas, `list` widget `rowTransitions` can send targeted `{ "patch": [ ... ] }` payloads. Not on the start transition, event transitions, `sensitive` inputs or `?async=true`. Examples: `update-billing-contact` and `patch-payment` in `invoice-collection.json`; full examples in [`docs/citizen-developer-guide.md`](../citizen-developer-guide.md) and the [README](../../README.md#updating-data-with-a-json-patch-inputformat-jsonpatch).
     - **Reactive form field rules (`visibleWhen`, `requiredWhen`, `disabledWhen` & `ui.<field>`)**: Schema properties in `start.input.schema.properties` and `transition.input.schema.properties` support `"visibleWhen"` (or `"x-visibleWhen"`), `"requiredWhen"` (or `"x-requiredWhen"`), and `"disabledWhen"` (or `"x-disabledWhen"`). These evaluate portable expressions against `ui.<field>` (the live value selected/typed in the open form before clicking Save/Submit), `data.<field>` (the persisted workflow instance data, falling back to `ui` on start forms), and `user` (`user.IsInRole("manager")` of the authenticated caller, defaulting to anonymous). Both frontends reactively show/hide, require, or disable fields as the user edits the form, and `JsonSchemaValidator` enforces all three on the server (stripping hidden fields from the input payload so unvalidated values never enter `instance.Data`, enforcing `requiredWhen` unless the field is hidden or disabled, and rejecting any attempt to modify a disabled field away from its persisted `data.<field>` or schema `default` with `$.<field>: is disabled.`):
       ```json
       "segment": { "type": "string", "title": "Müşteri Segmenti", "enum": ["Bireysel", "KOBİ", "Kurumsal"], "default": "Bireysel" },
       "taxOffice": {
         "type": "string",
         "title": "Vergi Dairesi",
         "visibleWhen": "ui.segment != \"Bireysel\"",
         "requiredWhen": "ui.segment == \"Kurumsal\"",
         "disabledWhen": "data.segment == \"Kurumsal\" && !user.IsInRole(\"manager\")"
       }
       ```
     - Dynamic dropdown lookups against another workflow's data:
       ```json
       "customerKey": {
         "type": "string",
         "title": "Müşteri",
         "x-lookup": {
           "entity": "CustomerOnboarding",
           "valueField": "key",
           "textField": "fullName"
         }
       }
       ```

4. **Triggers**:
   - `Manual` (buttons), `Automatic` (`rule` / `default`), `Scheduled` (`after` / `at`) and `Event`: `"trigger": "Event", "event": "payment.received"` runs when a message of that name is delivered to the instance (`WorkflowEngine.DeliverMessageAsync`, `POST /api/workflows/{key}/instances/{id}/messages/{name}` or `POST /api/workflows/{key}/messages/{name}?key=<business key>`). The message body is the transition `input`; several event transitions may listen for one message and the first whose `rule` holds (it can read `input`) runs. Event transitions are never shown as buttons. The sender needs the transition `roles`; `?bufferFor=PT10M` keeps a message the instance cannot take yet. The start transition cannot be an event transition.

5. **Tasks**:
   - Built-in tasks: `set`, `setKey` (business key once known, optional `ensureUnique: true`), `log`, `http` (requires an explicit absolute URL, respects `AllowedHttpHosts`, no redirects; supports `into` for full `{ statusCode, isSuccess, body, headers }` envelope or `select` / `output` field array/mapping object to write only selected parts of `result.body.*` / `result.statusCode` into `instance.Data`), `publish`, `rabbitmq`, `operation`, `startWorkflow` (sync or async subflow), `loadWorkflow` (loads another workflow instance's JSON data, `select` projection array or mapping object, optional `includeAgents: true` and `includeHistory: true` by `key`/`id`/`where` into scope), `queryWorkflow` (queries multiple instances across workflows using unified `where` expressions with automatic PostgreSQL partition index pushdown, `orderBy`, `select`, `first`, and `aggregate` `count`/`sum`/`avg`/`min`/`max`), `updateWorkflow` (updates single or `all: true` workflow instances by `key`/`id`/`where` via `values` expressions referencing `target.*` & `data.*`, `merge`, or RFC 6902 `patch`), `triggerWorkflow` (executes a `transition` with optional `runAsync: true` or delivers an `event` message with optional `bufferFor` on single or `all: true` workflow instances and stores the result into `into`), `fanOut` (parallel execution of `subTask` over `items` with `maxConcurrency` and `into`), `cache` (cache-aside execution of `subTask` by `key` with `ttl` and `into`), `agent` / `aiAgent` (Microsoft Agent Framework `single`/`sequential`/`concurrent`/`handoff` execution with `tools`, `mcpServers`, `outputSchema`, `maxToolCalls`/`maxTotalTokens` budgets, automatic state-aware transition discovery/routing, and dedicated persistence in `WorkflowAgentSessions` / `WorkflowAgentRuns` / `WorkflowAgentToolCalls`), and `mcp` (Model Context Protocol `callTool`, `listTools`, `readResource`, `listResources`, `getPrompt`).
   - Declarative AI tools (`Agents/Tools/*.json`) can execute portable expressions (`kind: "expression"`), any registered `IWorkflowTask` (`kind: "task"`, `"task": "set" | "cache" | "http" | "operation" | "loadWorkflow" | "queryWorkflow" | "updateWorkflow" | "triggerWorkflow" | ...` with `into` and optional `writeToWorkflowData: true`), HTTP calls (`kind: "http"`), or MCP tools (`kind: "mcp"`), and support optional `roles` for RBAC gating.
   - **Unified Input / Output / Set / Into Conventions**:
     - **Outgoing input (`input` / `data` / `body` / `payload` / `arguments`)**: `transition.input`, `subFlow.input`, `startWorkflow` (`data`/`input`), `triggerWorkflow` (`input`/`data`/`payload`), `http` (`body`/`payload`/`input`), `operation` (`input`/`args`/`payload`), `mcp` (`arguments`/`args`/`input`), `publish` & `rabbitmq` (`payload`/`body`/`message`/`input`/`data`).
     - **Expression assignment (`set` / `values`)**: `transition.input.set` (or `values`), `set` task (`values` or `set`), `updateWorkflow` (`values` or `set`).
     - **Target container path (`into`)**: `transition.input.into`, `subFlow.into`, and `into` across all tasks.
     - **Selective field projection & mapping (`select` / `output`)**: interchangeable across `subFlow`, `http`, `loadWorkflow`, `queryWorkflow`, `updateWorkflow`, `triggerWorkflow`, `startWorkflow`, `operation`, `mcp`, and `agent` (accepts either a field array `["a", "b"]` or a mapping object `{ "targetPath": "result.score * 2" }`).
   - **HTTP envelope (`input.header`, `input.query`, `input.body`)**: For requests arriving over `WorkflowEndpoints`, `WorkflowHttpInput` wraps the body: **every request header** (original name, lowercase, camelCase and `x-` stripped camelCase – including `Authorization` and `Cookie`), every query parameter (`input.query.branchId`) and the body (`input.body.*`, also copied to the `input` root) are in expression and task scope; values are parsed as number / boolean / text. Built-in audit fields: `input.header.correlationId`, `traceId`, `spanId`, `clientIp`, `userAgent` (see `commercial-limit-revision.json`). Only `body` is validated by `input.schema` and only what you `set` into `data.*` is persisted – never copy header or query values into `data` blindly, and treat them as untrusted (a client can send any `X-Branch-Id`).
   - **Long calls**: mark a state `onEntry` task `"background": true` (not in finish or SubFlow states, not `setKey`). The state commits first and the instance stays Active; the task runs as a job outside the lock, its data changes are merged when it finishes, then the remaining `onEntry` tasks and automatic transitions run. A failure follows the task's `onError` (`Fault` → `retry` runs it again). Background tasks receive no transition `input`.
   - **Record lifecycle** (master data such as `customer-onboarding.json`): don't finish immediately after creation – set the business key with `setKey`, stay in a `Human` `Active` state with update (`update-income`, `add-kyc-note`) or close (`close-account`) transitions, and expose the active instances as a directory via `WorkflowInstanceDataQuery` (`/api/v1/CustomerOnboarding/getitems` / `/getall`).

6. **Partitioning & indexing**:
   - Declare filterable fields in `dataSchema.properties` with explicit types (`integer`, `number`, `boolean`, `string`). The engine automatically creates dedicated PostgreSQL partition tables (`WorkflowInstances_{Suffix}`, `WorkflowInstanceData_{Suffix}`, `WorkflowJobs_{Suffix}`, `WorkflowHistory_{Suffix}`, `WorkflowIncidents_{Suffix}`, `WorkflowAgentSessions_{Suffix}`, `WorkflowAgentRuns_{Suffix}`, `WorkflowAgentToolCalls_{Suffix}`) at startup or when deployed via `POST /api/workflows/definitions`. A typed functional B-Tree index `IX_Part_{Suffix}_{prop}` on `"Data"` is created **only** for properties with `"x-index": true`, or with `x-search` **and** an `enum` / `number` / `integer` / `boolean` type (`WorkflowPartitionManager.ExtractIndexedProperties`); `start.input.schema` is not inspected, and `x-mask` or `"x-index": false` properties are never indexed. A global `jsonb_path_ops` GIN index exists on `WorkflowInstanceData.Data` and `WorkflowHistory.Data` (no trigram index). Indexes named `IX_Part_{Suffix}_*` that are not in the computed set are **dropped** on every deploy/startup – never use that prefix for hand-written indexes.
   - See [`workflow-partitioning-and-indexing.md`](workflow-partitioning-and-indexing.md) for architecture, partition-wise joins, and custom indexing patterns.

7. **Governance, Simulation & Operations**:
   - **Immutable Runtime Versioning & Running Instance Migration**: Saving a definition via `PUT /api/workflows/{workflow}/definition` automatically creates a new immutable version (`v2`, `v3`, …) when the workflow already exists, preserving the active version for running instances. Inspect versions (`GET /api/workflows/{workflow}/versions`), diff two versions (`GET /api/workflows/{workflow}/diff?fromVersion=1&toVersion=2`), roll back the active version (`POST /api/workflows/{workflow}/versions/{version}/rollback`), or migrate running `Active`/`Faulted` instances to a target version with optional `stateMap` (`oldState -> newState`) and `dryRun: true/false` (`POST /api/workflows/{workflow}/migrate`, or via the **🔄 Sürüm & Göç** tab in `/workflow-admin`).
   - **Human Task Claim, Unclaim & Multi-User / Role Delegation**: Transitions support static role names, dynamic `$role:<expr>`, direct user `$user:<expr>`, `$starter` / `$owner`, `$previousUser` (4-eyes via `denyRoles`), and `$assignee` in `roles` / `denyRoles`. At runtime, active instances support `POST /api/workflows/{workflow}/instances/{id}/claim` (`🙋 Üzerime Al`), `POST .../unclaim` (`🔓 Görevi Bırak`), and `POST .../assign` (`↪️ Devret / Ata`, accepting `{ "assignedTo": "..." }`, `{ "users": ["alice", "bob"] }`, or `{ "roles": ["committee"] }` / `"role:committee"` / `"@committee"`). Moving to a different state (`target != from`) clears `AssignedTo` and `AssignedAt` automatically.
   - **Dry-Run Simulation**: Test transitions, rules, expressions, and JSON Schema validations without writing to the database or calling external side effects via `POST /api/workflows/{workflow}/simulate`.
   - **Unified Inbox & Operations**: Query actionable human tasks across all workflows (`GET /api/workflows/inbox?assignment=all|mine|unassigned|claimed`), inspect faulted instances/incidents/jobs (`GET /api/workflows/operations`), or batch-retry faulted instances (`POST /api/workflows/operations/retry-batch`).
   - **Bundles & Retention Purge**: Export/import workflow definitions (`GET /api/workflows/bundle`, `POST /api/workflows/bundle/import` – the bundle carries definitions only; layouts and agent catalogs are deployed through `POST /api/ui/layouts/seed` and `POST /api/agents/catalog`), and purge old `Completed` / `Cancelled` instances (`POST /api/workflows/maintenance/purge`, `ui-admin`).

8. **Verify**:
   - Run `dotnet test --project tests/Middt.Framework.Tests -- --filter-class "*WorkflowDefinitionTests" --filter-class "*UiSampleLayoutTests" --filter-class "*SampleJsonWorkflowTests"`.
   - Click through both frontends (`/workflow/{key}`).

For a transition that accepts secrets, declare each top-level secret property in `input.sensitive`. The engine strips those values from persisted history and pending input, and rejects asynchronous execution of such transitions.
